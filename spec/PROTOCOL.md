# Vigilact 0.1 Experimental Protocol (Draft)

Status: **experimental, non-normative draft**. This document describes the currently implemented HTTP/JSON profile; it does not claim to be an industry standard. The key words **MUST**, **MUST NOT**, **SHOULD** indicate intended interoperability requirements for this profile.

## 1. Roles and trust

- **Agent**: authenticated principal that proposes a contract, publishes evidence and advertises capabilities.
- **Observer**: server that accepts a supported commitment, persists it and evaluates received evidence.
- **Operator**: authenticated principal authorized to read evaluation events and request invocable capabilities.

A principal is named with 1-64 ASCII alphanumeric, `_`, `-` or `.`, starting alphanumeric. The HTTP binding uses `X-Vigilact-Principal` and `X-Vigilact-Key`. Static keys are an alpha-only authentication mechanism; the specification does not require other implementations to store credentials in the same way.

## 2. Contract proposal

`POST /v1/contracts` accepts:

```json
{
  "client_ref": "nightly-001",
  "subject": "backup://device-1",
  "observation": {
    "kind": "expected_event",
    "event_type": "backup.completed",
    "deadline_at": "2030-01-01T02:30:00Z"
  }
}
```

The server MUST bind the accepted contract to the authenticated agent, **not** to a user-controlled `owner` field. It MUST reject a deadline already elapsed. It MUST return a server-generated UUID, the accepted terms, time of acceptance and state `ACTIVE`, with outcome `PENDING`.

For v0.1, negotiation means exact-term acceptance or rejection. **There are no counter-proposals or contract revisions.** An agent MUST use a new `client_ref` for a new occurrence. For the same principal, `client_ref` is an idempotency key: identical proposals return the same contract; different terms return HTTP 409.

A contract remains `ACTIVE` when its one-shot outcome becomes `SATISFIED` or `NOT_OBSERVED`; this status models an agreement persisted by the observer, not a reusable schedule. No contract expiry, suspension or revocation is implemented in this version.

## 3. Observation semantics

Only `expected_event` is supported:

- The agent promises that an event with matching `type` and `subject` will be **received** by the observer after acceptance and no later than `deadline_at`.
- `accepted_at` and `received_at` are generated by the server in UTC.
- An event can satisfy the commitment only if its authenticated owner matches the contract owner.
- For this experimental profile, a server MUST use **receipt time** for the deadline, regardless of the optional event `time` attribute.
- If the server's current time becomes strictly greater than the deadline while the outcome is pending, the observer MUST resolve it to `NOT_OBSERVED` and produce one evaluation event.
- After resolution, subsequent evidence MUST NOT retroactively rewrite the outcome. It MAY be stored for later audit.
- Absence of timely evidence MUST NOT be interpreted as proof that the underlying action did not run.

This profile intentionally uses **one-shot** deadlines, with no cron syntax, grace interval, event-time watermarks or distributed clock agreement. Server downtime can delay the publication of an observation; after restart the reference server reconciles expired pending contracts using its current clock. A recovered result identifies when the observation was made, not when the action actually failed.

## 4. Evidence format

`POST /v1/events` accepts a **restricted JSON subset** of the CloudEvents 1.0 envelope:

```json
{
  "specversion": "1.0",
  "id": "run-001",
  "source": "urn:vigilact:agent:device-1",
  "type": "backup.completed",
  "subject": "backup://device-1",
  "datacontenttype": "application/json",
  "data": {"duration_s": 12}
}
```

The reference implementation requires `source` to equal `urn:vigilact:agent:{authenticated-agent}`. Both `type` and `subject` must match the contract. Other CloudEvents extension attributes are currently rejected; binary data and `data_base64` are not implemented. This is **not full CloudEvents support**.

The pair `(source, id)` uniquely identifies an event. Repeated identical messages return `status=duplicate`; reuse of the same pair with different data returns HTTP 409. If multiple pending contracts of the same owner have the same `type` and `subject`, a single timely event may satisfy each of them. Producers should therefore use sufficiently distinct subjects for distinct jobs.

## 5. Evaluation events

When a commitment resolves, the observer appends one CloudEvents-style event to a durable outbox:

- `dev.vigilact.observation.satisfied`
- `dev.vigilact.observation.not_observed`

`GET /v1/outbox?after=<cursor>&limit=<n>` returns ordered entries and a `next_cursor`. This is an **at-least-once consumer pattern**: a consumer stores its cursor **after** handling each event. No broker, push notification, webhook or consumer acknowledgement is included in the profile.

## 6. Capability description and invocation

`PUT /v1/agents/me/capabilities` replaces the current manifest for an agent:

```json
{
  "capabilities": [
    {"name":"backup.status", "mode":"query", "invocable":false},
    {"name":"backup.retry", "mode":"command", "invocable":true}
  ]
}
```

Capabilities are descriptive metadata, not executable code. Only commands with `invocable=true`, advertised by the target agent, can be queued by authenticated operators. This is **not** a complete permissions system for production. Agents MUST additionally allow-list the command handler locally, validate arguments and enforce their own authorization policy.

Lifecycle: `PENDING` → `CLAIMED` → `SUCCEEDED` or `FAILED`.

- Operators submit `POST /v1/commands` with a unique `request_id`.
- Agents poll `GET /v1/agents/me/commands`, then atomically claim an item.
- Agents explicitly post an execution result; the server does **not** execute arbitrary commands.
- Repeated identical requests/results are idempotent; conflicting repeats return HTTP 409.
- Requests specify `ttl_seconds` (default 300, range 1..86400); unclaimed commands expire and cannot subsequently be claimed.
- A claim sets a 120-second lease; after it passes without a result the status becomes `UNKNOWN`, and the command is **never automatically requeued**. The original agent may still report a late result.
- Revoking a previously invocable capability cancels unclaimed pending commands. Claimed actions may remain indeterminate; never blindly retry them.
- The original requesting operator can inspect `GET /v1/commands/{id}`. These rules are a Python-only experimental extension, **not** part of Core conformance.

## 7. Endpoint summary

| Method / path | Authorized role | Meaning |
| --- | --- | --- |
| `GET /v1/info` | public | Implementation and profile discovery |
| `POST /v1/contracts` | agent | Propose/accept a contract |
| `GET /v1/contracts/{id}` | owner agent / operator | Read current outcome |
| `POST /v1/events` | agent | Submit evidence |
| `GET /v1/outbox` | operator | Read observer evaluation events |
| `PUT /v1/agents/me/capabilities` | agent | Replace capabilities |
| `GET /v1/agents/{agent}/capabilities` | owner agent / operator | Read capabilities |
| `POST /v1/commands` | operator | Queue an authorized request |
| `GET /v1/commands/{id}` | requesting operator | Inspect command state and result |
| `GET /v1/agents/me/commands` | agent | Poll pending requests |
| `POST /v1/agents/me/commands/{id}/claim` | target agent | Claim a request |
| `POST /v1/agents/me/commands/{id}/result` | target agent | Resolve a request |

As of reference implementation 0.4.0a1, HTTP errors are represented using
`application/problem+json` with the `error` extension. The response `type`
identifiers and error vocabulary are still experimental. See [ERRORS.md](ERRORS.md).
A fully stabilized RFC 9457 error registry remains future work.

## 8. Protocol compatibility

The `/v1` path labels the initial HTTP route family, not a promise of a frozen v1 standard. Clients SHOULD check `/v1/info`. Breaking changes are expected until a non-experimental release and may require migration.

## 9. What the observer guarantees

The reference server commits contract acceptances, event ingestion and outcome/outbox updates using SQLite transactions. It does not guarantee timely wake-up under process downtime, storage failure, clock changes, or network partitions. `SATISFIED` proves a matching event was accepted by the server within the contract window, **not** that the producer's claim was correct. See `SECURITY.md` and `spec/CONFORMANCE.md`.

## 10. Reference implementation hardening (0.4.0a1)

The protocol profile remains `vigilact/0.1-experimental`. New operational
safeguards in the reference HTTP binding are separate from wire-level
standardization:

- Remote command endpoints require explicit server enablement (`VIGILACT_ENABLE_COMMANDS=true`)
  **in addition** to agent opt-in and the operator role. They return HTTP 403
  with `error=commands_disabled` otherwise. They may still appear in OpenAPI;
  the `/v1/info` `profiles` and `features.remote_commands` reflect runtime availability.
- Request bodies larger than `VIGILACT_MAX_REQUEST_BYTES` (default 262144)
  receive HTTP 413. This is an implementation safety limit, not a normative
  requirement of the transport-neutral protocol.
- Error responses use `application/problem+json` with a short, backward-compatible
  `error` extension; see [ERRORS.md](ERRORS.md).

Do not infer production support from these protections. See [SECURITY.md](../SECURITY.md).

## 11. Wire-time precision (0.4.0a1)

Both reference observers accept RFC 3339 timestamps with explicit timezone and
at most six fractional-second digits. Epoch numbers and naive datetimes are
rejected on the HTTP boundary. `CloudEvent.time` cannot backdate evidence.
See the [timestamp conventions](../docs/concepts/wire-timestamps.md).
